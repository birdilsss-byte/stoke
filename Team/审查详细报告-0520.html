项目定位结论

低频个人量化数据中间件。6 大数据源整合框架完整，Store 缓存策略合理（TTL 分级 + 故障降级 + 预热机制），时机层和发现层的注意力机制设计思路正确。架构契合场景，整体处于「可用但需治理」阶段。

最大的优点是克制——不用调度框架（一个函数）、不用 EventBus（一个 dataclass）、不用 Redis（SQLite 单文件）、不用全盘扫描（5 条注意力通道）。最大的风险是工程细节粗糙——P0 漏洞和 TTL 键名不一致若不修，时间长了会成为隐性炸弹。

二、P0 问题（必须立即修复）

P0 = 致命问题，影响正确性或安全性，必须 24-48 小时内修复。

P0 SQL 注入风险

store.py _read() / _write() / _is_fresh() 多处使用 f-string 拼接表名列名：f'SELECT * FROM "{table}" WHERE "{key_column}" = ?'

风险：攻击者可构造恶意表名列名（如 "; DROP TABLE kline_daily; --"）执行任意 SQL

修复方案

# 表名列名白名单校验
import re
_VALID_IDENTIFIER = re.compile(r'^[a-zA-Z_][a-zA-Z0-9_]*$')

def _validate_identifier(name: str) -> str:
    if not _VALID_IDENTIFIER.match(name):
        raise ValueError(f"非法标识符: {name}")
    return name

修复 表名列名加入正则白名单校验，不合格则抛 ValueError

P0 sources/__init__.py 导出不完整

sources/__init__.py __all__ 只导出 3 个类，但项目实际使用了 6 个 Source

# 当前（不完整）
__all__ = ["MootdxSource", "AKShareSource", "TencentSource"]

# 实际使用但未导出
BaostockSource  ← timing.py、client.py 多处使用
EFinanceSource   ← client.py、client_cached.py 使用
ZhituSource      ← client.py 使用

修复 补全 __all__ 列表包含全部 6 个类

P0 runner.py 注释与代码不一致

runner.py L26 注释说「默认 StokeCached」，但 L33 写 s.store.warmup(s._s) 暗示实际需要 StokeCached

# L26 当前注释（误导）
s = Stoke()  # 默认 StokeCached（带缓存）

# L33 实际调用
s.store.warmup(s._s)  # 需传裸 Stoke 实例避免缓存回环

修复 修正注释：# 默认 StokeCached（带缓存）， # warmup 需传裸 Stoke 实例（._s）避免缓存回环

三、P1 问题（高优先级）

P1 = 影响数据正确性或系统稳定性，建议 1 周内修复。

P1-1 TTL 键名不一致（连字符 vs 下划线混用）

store.py + client_cached.py

Store 层定义："klinedaily" / "marketbreadth" / "sector_rank" / "strongstocks" 混用连字符和下划线

warmup 中 fallback 逻辑 TTL.get(table_name.replace("_", "")) 掩盖了部分键名错误

修复 统一改为下划线命名（kline_daily、market_breadth、sector_rank 等）

P1-2 Store 层与 Client 层双向隐式耦合

store.py warmup() 依赖传入裸 Stoke 实例，且使用 ._s 私有属性

违反依赖倒置原则（Store 应依赖抽象接口而非具体 Client 实现），且测试困难

修复 引入 DataFetcher Protocol 接口，warmup 依赖抽象而非具体类

P1-3 Client 类职责过载（God Class）

client.py 单一类 48 个方法，涵盖：行情/新闻研报/信号/情绪/资金流/估值/智兔数服

难以单独测试某个数据域，新增数据源必须改主类

修复 按业务域拆分为 market / signal / sentiment / fund / valuation 子模块

P1-4 mootdx 连接失败无降级

mootdx_source.py Quotes.factory() 失败时直接抛异常，无友好提示

修复 捕获异常，抛出 SourceNotReadyError 并提示检查通达信客户端是否安装

P1-5 缓存降级无幂等保护

client_cached.py Store 损坏时每次请求都触发 except 分支重试网络，可能触发数据源限流封禁

修复 加 _degraded 标志，首次降级后设置标志，后续请求直接透传

P1-6 时机层权重硬编码

timing.py 五维权重写死在 assess() 中，无法切换保守/激进策略

修复 权重抽到 config.py 的 TIMING_WEIGHTS 字典，Timing.__init__() 接受 profile 参数

P1-7 限流器多线程不安全

rate_limiter.py last_request_time 实例变量在多线程并发下存在竞态条件

修复 添加 threading.Lock()，或使用 time.monotonic() 替代 time.time()

P1-8 重试装饰器异常信息丢失

utils.py retry_on_empty=True 且 DataFrame 为空时，last_exc 可能未赋值，raise last_exc 抛 None

修复 函数开头初始化 last_exc = None，确保总是有可抛出的异常

P1-9 交易日历缓存永不刷新

calendar.py _load_trading_days() 永久缓存在内存中，春节调休调整后程序需重启才能更新

修复 添加时间窗口校验（如首次加载后超过 7 天则重新加载），或提供手动刷新接口

P1-10 warmup 中日期 key 切分 Bug

store.py L356 日期字符串切分错误

# 当前（错误）
f"{key[:4]}-{key[2:4]}-{key[4:]}"
# 输入: "20260521"
# 期望: "2026-05-21"
# 实际: "2026-0521"  ← 月份丢了一位！

修复 修正为 f"{key[:4]}-{key[4:6]}-{key[6:]}"

P1-11 mootdx 连接状态管理不完善

baostock_source.py 网络异常后 _logged_in 标志可能与服务器状态不同步

修复 每次调用前验证连接有效性，失败后主动重连

四、P2 问题（中优先级）

P2 = 不影响可用性，但影响代码质量和长期可维护性，建议在下一迭代修复。

编号问题描述文件修复建议
P2-1 Normalizer 模块定义了但未被实际使用，列名规范化散落在 client_cached.py 各方法的 column_map 参数中 normalizer.py 在 Sources 层返回前统一调用 normalizer，集中管理列名映射
P2-2 exceptions.py 定义了异常体系但各数据源未统一使用（抛出的是标准 Exception 而非 StokeError 子类） 各 source 文件 数据源按异常类型抛出对应 StokeError 子类，上层可差异化处理
P2-3 config.py 的 setup_logging() 在模块导入时自动执行（client_cached.py L18），违反延迟初始化原则 config.py 改为惰性初始化，或提供 setup_logging(lazy=True) 参数
P2-4 _is_fresh() 的 key 过滤逻辑不精确，replace 模式的每日快照可能返回旧日期数据（MAX(fetched_at) 不过滤特定 key） store.py 按 key_column 和 key 过滤后再判断新鲜度
P2-5 Store 缺少数据版本迁移机制，表结构变更需手动处理 store.py 建立 MIGRATIONS 字典记录版本历史，支持 ALTER TABLE

P2-7 发现层评分过于简化（仅基于连板数，忽略换手率/量比/封单金额） discovery.py 引入多因子评分模型，综合考虑换手率、封单量、题材热度等
P2-8 Context 类型安全缺失（candidates: list 无具体类型），行业轮动通道返回 symbol 为空 context.py 定义 Candidate dataclass，统一所有通道的返回结构
P2-9 行业维度 _assess_sector() 中列名判断逻辑脆弱，多处 fallback 回退到 50.0 timing.py 统一依赖 normalizer.py 返回的标准化列名，减少 fallback 分支
P2-10 rename(..., inplace=True) 在 pandas 3.0+ 已弃用 store.py 改为 df = df.rename(columns=...)
P2-11 baostock 健康检查日期硬编码为 "2026-05-20"，非交易日会失败 baostock_source.py 使用 today_str() 替换硬编码日期
P2-12 efinance_source.py 中 symbols=None 时 len(symbols) 触发 TypeError efinance_source.py 改为 len(symbols) if symbols is not None else 0
P2-13 akshare 市场判断逻辑对 8 开头（沪 ETF）等处理不当，仅判断 startswith("6") akshare_source.py 扩展判断逻辑覆盖 0/3/8/4/9 等开头代码
P2-14 TencentSource 类名误导（实际通过 akshare 获取数据） tencent_source.py 更名为 ValuationSource 更准确
P2-15 多个 lambda 闭包变量捕获存在隐患（部分 lambda 使用默认参数正确，部分可能有问题） 多个文件 统一检查所有 lambda，确保闭包变量正确捕获
P2-16 多进程/多线程扩展能力缺失（RateLimiter 实例变量、MarketContext 无锁保护、SQLite 并发写入有限制） 整体架构 预留 Store(backend="redis") 扩展点，未来需要时重构

七、架构总评与总体结论

设计哲学正确，具体实现有瑕疵

项目最大的优点是克制：不用调度框架（一个函数）、不用 EventBus（一个 dataclass）、不用 Redis（SQLite 单文件）、不用全盘扫描（5 条注意力通道）。这种克制是低频个人量化场景的正确选择。

时机层 + 发现层的克制之道

时机层的五维加权模型（大盘/估值/行业/情绪/资金流）用固定权重替代了复杂的多因子动态配置——对于个人低频量化来说，这是正确的工程权衡。北向资金通道只记录方向不展开个股，体现了「知道边界在哪里」的克制。

发现层的注意力机制从「选股」变成「跟随市场选出的标的」——这是认知上的根本转变，也避免了「构建完美选股模型」这个几乎无解的问题。

最大的架构风险

不是架构设计，而是工程细节的粗糙度。Client 的膨胀路径（48 个方法）是个人项目的常见陷阱——因为「加一个方法很容易」，所以文件会无限膨胀。P0 SQL 注入和 TTL 键名不一致若不修，时间长了会成为隐性炸弹，且极难排查。

最终建议

建议 修完 4 个 P0/P1-10，立刻进入实际使用阶段。在实战中发现问题、解决问题，比闭门清理工程债务更有效率。等时机层和发现层在实际交易中产生反馈数据后，再针对性优化评分模型，比现在空对空设计更有效。
