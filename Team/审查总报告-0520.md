## 二、P0 问题（必须立即修复）

共发现 **2 个 P0 问题**，均为严重 bug：

### P0-1：SQL 注入风险（安全漏洞）

| 项目 | 内容 |
|------|------|
| 文件 | `stoke/store.py` |
| 位置 | `_read()`、`_write()`、`_is_fresh()` 等多处 |
| 问题 | 使用 f-string 拼接表名列名到 SQL 语句：`f'SELECT * FROM "{table}"'`、`f'WHERE "{key_column}" = ?'`，未校验标识符合法性 |

### P0-2：sources/__init__.py 导出不完整

| 风险 | `from stoke.sources import *` 无法导入全部类，部分代码依赖隐式导入维持 |
| 修复 | `__all__` 补全 6 个 Source 类 |

### P0-3：runner.py 注释与代码不一致（审查中新增）

| 项目 | 内容 |

| 风险 | 维护者误解启动流程 |
| 修复 | 修正注释：`# 默认 StokeCached（带缓存），warmup 需要传裸 Stoke 实例以避免缓存回环` |

## 四、P2 问题（中优先级，建议修复）

共发现 **16 个 P2 问题**：

### 数据层（5 个）
- `Normalizer` 模块定义了但未被实际使用，列名规范化散落在 `client_cached.py` 各方法的 `column_map` 参数中
- `exceptions.py` 定义了异常体系但各数据源未统一使用
- `config.py` 的 `setup_logging()` 在模块导入时自动执行，违反延迟初始化原则
- `_is_fresh()` 的 key 过滤逻辑不精确，replace 模式的每日快照可能返回旧日期数据
- `Store` 缺少数据版本迁移机制，表结构变更需要手动处理

### 时机层 / 发现层（5 个）
- 时机层五维打分对 NaN 数据处理不足（MA 计算数据不足 5 条时返回 NaN，后续比较出错）
- 发现层评分过于简化（仅基于连板数/题材归因，忽略换手率/量比/封单金额）
- Context 类型安全缺失（`candidates: list` 无具体类型，行业轮动通道 symbol 为空）
- 行业维度 `_assess_sector()` 中列名判断逻辑脆弱
- 资金流维度 `_assess_fund_flow()` 中单位硬编码（假设数据单位为元）

### 代码质量（6 个）
- pandas `rename(..., inplace=True)` 在 pandas 3.0+ 已弃用
- `baostock_source.py` 健康检查日期硬编码为 `"2026-05-20"`
- `efinance_source.py` 中 `symbols=None` 时 `len(symbols)` 会触发 TypeError
- `akshare_source.py` 市场判断逻辑对 8 开头（沪 ETF）等处理不当
- `tencent_source.py` 类名误导（实际通过 akshare 获取数据）
- 多个 lambda 闭包变量捕获存在隐患

## 五、各层独立评估

### 数据层（client.py / store.py / sources/）

**评分：7.5/10**

6 大数据源整合框架完整，Store 缓存策略合理（TTL 分级 + 故障降级 + 预热机制），符合低频量化场景。P0 SQL 注入和 P1 键名不一致是主要隐患。

### 时机层（timing.py）

**评分：7.0/10**

五维加权模型设计合理（大盘/估值/行业/情绪/资金流），权重分配符合逻辑。失败时统一返回 50.0（中性分）的降级策略合理。主要缺陷是权重硬编码和 NaN 处理。

### 发现层（discovery.py）

**评分：6.5/10**

5 条注意力通道的实现思路正确（涨停板/强势股/热搜概念/北向资金/行业轮动），北向资金通道目前只记录方向、尚未展开个股是合理的克制做法。评分模型过于简化是主要短板。

### 主流程（runner.py + context.py）

**评分：8.0/10**

`MarketContext` 作为轻量值对象传递状态，比全局 dict 和 EventBus 都更简洁。`daily_routine()` 4 步流程清晰简洁，风控跳过逻辑正确。注释与代码不一致是唯一缺陷。

## 六、架构总评

**设计哲学正确，具体实现有瑕疵。**

项目最大的优点是**克制**：
- 不用调度框架，用一个 `daily_routine()` 函数
- 不用 EventBus，用一个 38 行的 dataclass
- 不用 Redis/Memcached，用 SQLite 单文件
- 发现层不用全盘扫描，用 5 条注意力通道

这种克制是低频个人量化场景的正确选择。

最大的架构问题是**Client 的膨胀路径**：48 个方法 + 6 个数据源 + Store 缓存逻辑都集中在一个文件里。这是个人项目的常见陷阱——因为「加一个方法很容易」，所以文件会无限膨胀。建议尽快拆出 `client_cached.py` 作为独立文件（已有），并考虑按业务域拆分 Client。

## 九、总体结论

Stoke 项目在「低频个人量化」这个细分场景下，**架构设计是对的，核心路径是通的，数据基本是可用的**。

时机层和发现层的实现思路（注意力机制、五维加权）符合场景，没有过度工程。最大的风险不是架构设计，而是工程细节的粗糙度——SQL 注入、P0 漏洞、TTL 键名不一致这些问题如果不修，时间长了会成为隐性炸弹。

建议：**修完 3 个 P0 + 1 个 P1-10，立刻进入实际使用阶段**。在实战中发现问题、解决问题，比闭门清理工程债务更有效率。
